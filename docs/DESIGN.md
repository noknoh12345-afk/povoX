# povoX の設計

## 目的と前提

- povo2.0 のデータ残量を「ほぼ常に」把握し、足りなくなりそうなら手持ちのコード・トッピング購入で補う。
- 何をするかは利用者がルール(JavaScript)で決める。電池・ネットワーク・時刻・残量の減り方などで判断を変えられる。
- お金が動くので、**ルールがどう書かれていても越えられない安全装置**を、ルールとは別の層に置く。
- iOS はアプリを常時動かせない。起こされる機会(バックグラウンド更新・ショートカット・表示中・通知)を組み合わせ、その時々で確実に判断する。

## 全体の形

```
┌──────────────────────────── iOS アプリ(Swift)────────────────────────────┐
│ 画面(SwiftUI)  通知(ボタン付き)  バックグラウンド更新  ショートカット  ウィジェット │
│        │              │                   │                │           ↑      │
│        └──────────────┴───── AutomationService ────────────┘     App Group   │
│                                 │        │                                    │
│                     ルールの評価(JavaScriptCore)  ← 読み取りとログだけ        │
│                                 │ 計画(JSON)                                 │
├─────────────────────────── UniFFI(型付き)────────────────────────────────┤
│                         PovoEngine(Rust、core/)                              │
│   安全装置・計画の実行・確認待ち・記録・履歴と予測・保存(1ファイル)            │
│                                 │                                             │
│                          povo-core(povo への通信)                           │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1回の自動チェック

1. **材料を集める**: エンジンが残量(30秒以内なら前回の値)・トッピング・減り方の予測・未使用コード・今月の予算をまとめる。アプリが電池・ネットワーク・時刻・きっかけを足す。
2. **ルールが判断する**: `decide(ctx)` が計画を返す。例: `firstOf(applyCode(), buy(1時間の使い放題), notify(...))`。ルールは povo へ送れない(ネイティブ関数は読み取りとログだけ)。3秒を超えたら止める。
3. **エンジンが実行する**: 計画の各手を安全装置にかけ、設定に従って **実行 / 通知で確認待ち / 試運転の記録 / 見送り** にする。
4. **後始末**: 通知(確認待ちには「実行する / やめる」ボタン)、ウィジェットの更新、次の自動チェックの予約。

同じ流れを「シミュレーション」(仮の状態・通信なし・記録なし)でも動かせる。シミュレーターと本番で判断がずれない。

## なぜこの形か(v1 からの変更)

| v1 | v2 | 理由 |
| --- | --- | --- |
| ルールが `povo.buy()` を直接呼ぶ | ルールは計画を返すだけ | 判断と実行を分けると、試運転・シミュレーション・説明(なぜ買った/買わなかった)が同じ仕組みでできる。ルールの不具合で二重に買うこともない |
| 自動か試運転か | しない / **通知で確認** / 自動 | 「確認してから」が既定なら、最初から安全に便利さを得られる。ロック画面のボタンで済む |
| JSON の受け渡し(手書きの型) | UniFFI の型付き API | Rust と Swift の型のずれ(v1 で `requires_3ds` の読み違いを見つけた)をコンパイル時に防ぐ |
| 毎回同じ間隔 | 減り方で間隔を調整 | なくなりそうなら短く、使い放題中は終わる頃に。余計な通信と電池を減らす |
| 残量だけ | 履歴・予測・グラフ | 「あと何時間もつか」で判断できる(`ctx.forecast.hoursLeft`) |
| 保存データを丸ごと読む | 項目ごとに読む | 形が変わっても、読めない項目だけを初期値に戻す。手持ちのコードを失わない |
| 確認はコードを読んで | シミュレータで画面テスト | CI で本物のアプリを起動し、全画面を操作してスクリーンショットを撮る |

## 安全装置(エンジン側、ルールから外せない)

povo-web から引き継いだもの:

- povo への通信は常に1本ずつ(エンジンの Mutex)。自動リトライなし。
- 403・PIN 要求で全部止まる。止まったことは保存され、バックグラウンド・ショートカット・通知からも越えられない。アプリで「通信を再開」を押すまで続く。
- povo が待機時刻を返したら、その時刻まで送らない。
- トークンの更新は期限切れ後だけ。端末IDとトークンは組で保存(キーチェーン、最初のロック解除後・この端末だけ)。
- 購入・コードは送る「前」に記録する。失敗しても自動では送り直さない。

自動化のために足したもの:

- 購入: 一覧に載っている・価格が読める・3DS 不要・月の上限・1日の回数・前回からの間隔・同じ商品は2分あける。
- コード: 未使用のものだけ・15秒に1回・使い放題中は送らない・使い放題中か分からないときも送らない。
- 1回の自動チェックで使う購入・コードは1つまで。確認待ちがある間は同じ種類を重ねて出さない。確認は既定30分で期限切れ。
- 確認ボタンを押したときも、実行の直前に安全装置をもう一度かける(その間に上限などが変わっているかもしれない)。
- povo への通信は5分間に20回まで。

## 状態の置き場所

| もの | 場所 | 備考 |
| --- | --- | --- |
| 端末ID・トークン | キーチェーン | エンジンが変化のたびに `SessionStore` 経由で保存 |
| 設定・コード・注文の記録・実行の記録・履歴・確認待ち | `Application Support/povoX/state.json` | エンジンが書く(一時ファイル→置き換え) |
| ルールの本文・アプリ側の設定 | UserDefaults | |
| ウィジェット用の残量 | App Group の共有フォルダ | ウィジェットは通信しない |

モックと本番は別のファイル(`state-mock.json`)。

## テスト

- `core/`: `cargo test`(モック)。計画の実行、確認待ち、上限、停止の保存、シミュレーション、レート制限、保存の互換性など。
- `tools/rule-harness.js`: アプリと同じ `rule-prelude.js` とテンプレートを Node で評価し、本物のエンジン(モック)で実行する。
- iOS シミュレータ(CI): 単体テスト(JavaScriptCore での評価、無限ループの停止、キーチェーン、自動チェックの流れ、ショートカット)と画面テスト(初回案内→ログイン→確認待ち→実行→履歴、ルール・シミュレーター、コード・トッピング・設定・ウィジェット、ダークモード、通知のボタンでの実行)。スクリーンショットとクラッシュレポートは `ci-artifacts` ブランチに置く。
- 実機向けの検査(CI): `tools/check-macho.py` で、実機向けの .app と2つの IPA の実行ファイルが読み込むライブラリ(LC_LOAD_DYLIB など)・LC_RPATH・対象(実機かシミュレータか)・最低 iOS を調べる。iOS のもの(`/System/Library`・`/usr/lib`)とアプリの中にあるもの以外を読み込んでいたら、IPA を公開しない。
- リリース構成での起動(CI): 実機と同じリリース構成でシミュレータ版を作り、`core/target` と `ios/RustLib` を隠してから、テスト用の起動オプションなし(本番と同じ起動の流れ)で起動し、12秒後も動いているか・クラッシュレポートが出ていないかを見る。
- 画面テストで見つけて直したもの: 通知の「実行する」でアプリが落ちる(async 版の通知 delegate が完了ハンドラを画面以外のスレッドから呼ぶ)、確認後も記録の要約が「確認待ち」のまま、ダークモードで白地に白文字のボタン、履歴のアイコンの選び方、見出しの大文字化。
- 実機で見つかったもの(build-9・10): 起動した瞬間に落ちる。`crate-type` に `cdylib` が入っていたため iOS 向けにも .dylib ができ、`-lpovo_auto` がそれを選んで、アプリが CI の Mac 上のパス(`/Users/runner/...`)のライブラリを読み込む作りになっていた。シミュレータはその Mac の上で動くので見つからなかった。

## レシピ(選ぶだけのプリセット)

- ルールを書かずに選べる 266 個のプリセット。レシピは**パラメータだけ**を持ち(`Resources/recipes.json`、作成は `tools/gen-recipes.py`)、実際のルール(`decide(ctx)`)は `RecipeCompiler` がパラメータから組み立てる。1つのレシピ源から大量の組み合わせを生むので、文面と挙動がぶれない。
- 安全装置はこれまでどおりエンジン側。レシピは「何をするか」だけを決める。
- 検証: 全 266 個が CI の単体テストで「構文 OK」かつ「10 場面で例外なく正しい計画を返す」ことを確認(ローカルでも Node で 266×16=4256 評価が全成功)。

## 動く場所の違い(iPhone / Mac / LiveContainer)

- `Runtime` が Mac(PlayCover など)・LiveContainer・iPhone を見分ける。機能は**名前で決め打ちせず可否で出し分ける**(App Group が使えるか、バックグラウンド更新が使えるか)。
- Mac・LiveContainer ではバックグラウンド更新・位置情報・ウィジェットが動かないので、`BackgroundScheduler` は no-op にし、画面に注意を出し、`povoX-nowidget.ipa` を使う。
- Mac はキーボードで操作(⌘1〜5 / ⌘R / ⌘Return)。

## 位置情報での起動

- `LocationMonitor` が significant-location-change と visit 監視を使い、移動・立ち寄りを合図に自動チェックを回す(アプリが閉じていても起こされる)。位置の値は使わず povo にも送らない。
- Core Location は追加の署名(entitlement)が要らないので、無料 Apple ID でも使える。`allowsBackgroundLocationUpdates` は false のまま(連続測位はしない)。

## 無料 Apple ID の制約(正直に出す)

- VPN／ネットワーク拡張・プッシュ通知は無料 Apple ID では署名できない。よって「ほかのアプリの通信を止める」はこの端末ではできない。代わりに iOS 設定への近道と「知らせるだけ」レシピを案内する。
- povo のローミング等の変更は料金に直結するため povoX からは自動で変えず、公式アプリ/サイトへ誘導する。

## 本家の閲覧機能(請求・紹介・プロフィール)

- 公式アプリ 1.69.0 の解析で差分を把握。足りなかった閲覧系を povo-core 経由で追加:`bills`/`bill_pdf`・`referral`・`account_profile`。すべて読み取りで、お金は動かさない。

## Rust のエンジンの組み込み方

- `core` は `staticlib`(アプリ用)と `lib`(テスト用)だけを作る。iOS 向けの .dylib は作らない。
- アプリは `ios/RustLib/<sdk>/libpovo_auto.a` をパスで直接リンクする(`-l` で探させると .dylib が優先される)。
- Swift の型を作るときだけ、`cargo rustc --lib --crate-type cdylib` でビルドした Mac 向けの .dylib を uniffi-bindgen に読ませる。
